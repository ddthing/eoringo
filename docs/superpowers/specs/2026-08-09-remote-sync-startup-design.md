# Remote sync startup design

## Decision

The remote sync runtime creates its store bridge before the first startup sync, with
local-store subscriptions deferred. The first remote response now hydrates the bridge
and establishes its remote revision index and local baseline. Subscriptions begin only
after that hydration succeeds.

## Why

Previously the runtime performed a second `startup` sync after attaching the bridge so
the bridge could see the remote documents. That repeated a remote document-list request
despite the first response containing the same data. The bridge now receives that first
response directly, so one successful startup sync is sufficient.

## Preserved behavior

- Writes remain suppressed while the initial remote state hydrates stores.
- Store subscriptions do not start until initialization has completed, as before.
- A failed startup stops the bridge and coordinator without subscribing to later writes.
- Focus, online, token-refresh, and local-write sync triggers are unchanged.

## Verification boundary

Unit tests use the mock sync coordinator. They verify exactly one startup sync and that
subscriptions start only after it resolves. Live Supabase traffic is intentionally not
generated by the standard test suite.
